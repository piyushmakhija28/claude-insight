# v2.0.0 Requirements Brief -- Hook-Free Plugin Transformation

**Status:** Draft requirement, not yet approved
**Author:** Piyush Makhija
**Date:** 2026-08-01
**Audience:** prompt-generation-expert (prompt manager) -> orchestration prompt -> implementing agents
**Target repo:** `claude-workflow-engine`
**Dependent repo:** `claude-global-library` (read-only consumer)

---

## 1. Purpose

Turn `claude-workflow-engine` from a hook-driven pipeline that fires on every prompt and every
tool call into an **explicitly invoked Claude Code plugin** that:

1. Knows and enforces this project's own policies (after auditing which ones are actually real).
2. Runs **without** `PreToolUse` / `PostToolUse` / `UserPromptSubmit` hooks.
3. Selects agents and skills from `claude-global-library` using the **master knowledge graph**,
   not hardcoded name lists.
4. Installs as a single plugin that gives any Claude Code session the engine's full capability set.

---

## 2. Current State (verified 2026-08-01 -- do not re-derive, but do re-verify before editing)

### 2.1 Hooks in force

`~/.claude/settings.json` registers five synchronous hooks, all pointing into this repo:

| Event | Script | Timeout | Matcher |
|-------|--------|---------|---------|
| UserPromptSubmit | `scripts/3-level-flow.py` | 120s | (all prompts) |
| PreToolUse | `hooks/pre-tool-enforcer.py` | 60s | `""` = every tool call |
| PostToolUse | `hooks/post-tool-tracker.py` | 60s | `""` = every tool call |
| Stop | `hooks/stop-notifier.py` | 60s | (all stops) |
| Notification | inline PowerShell beep | 15s | (all notifications) |

All are `async: false`. Every tool call therefore pays two synchronous Python process spawns,
and every user prompt pays up to a 120-second orchestration blocking window before Claude
sees the prompt. This is the cost the user wants removed.

### 2.2 Policies

- `docs/policies/` -- 46 markdown policy documents (the authored corpus).
- `~/.claude/policies/` -- 5 directories (`01-sync-system`, `02-standards-system`,
  `03-execution-system`, `failure-prevention`, `testing`); this is what `get_policies_dir()` reads.
- `policies/` in-repo -- contains **only** `03-execution-system/failure-prevention/failure-kb.json`.

So there are three policy locations with three different shapes, and the repo copy is nearly empty.

### 2.3 Library and master KG

`claude-global-library` currently holds **506 agents**, **993 skills**, **99 domains**
(master graph header self-reports 541 agents / 1030 skills / 99 domains at library v29.72.0 --
this drift must be resolved, see FR-9).

Master KG artifacts at `knowledge-graph/_master/`:
`super_graph.json` (3.0 MB), `agents_all.json`, `skills_all.json`, `edges_all.json`,
`domains_all.json`, `math_masters_all.json`, `indices/`, `schema.json`, `invariants.json`,
`validate.py`, `build_master.py`, `qa_report.json`.

## 3. Scope

### 3.1 In scope

- Policy comprehension pass + implementation gap audit (Workstream A).
- Removal of hook-based execution and replacement with explicit invocation (Workstream B).
- KG-driven agent/skill selection replacing any hardcoded selection (Workstream C).
- Packaging the engine as a distributable Claude Code plugin (Workstream D).

### 3.2 Out of scope

- Rewriting the 13 MCP servers (they stay in their own repos; the plugin only references them).
- Changing the LangGraph pipeline's *step semantics* (Steps 0-8 keep their meaning).
- Any change inside `claude-global-library` other than reading it. If the library needs a fix,
  raise it as a separate issue in that repo.
- Building a new knowledge graph. The master KG already exists and is the source of truth.

## 4. Workstream A -- Policy Comprehension and Implementation Audit

**FR-1: Read and internalise every policy before proposing any change.**
Read all 46 files in `docs/policies/`, plus everything under `~/.claude/policies/`, plus
`docs/standards/` (52 numbered rules). Do not skim. Produce a normalised inventory.

**FR-2: Produce a policy implementation matrix.**
One row per policy, with these columns:

| Column | Meaning |
|--------|---------|
| Policy ID / file | e.g. `docs/policies/quality-gate-policy.md` |
| Intent (one line) | what the policy claims to enforce |
| Enforcement point | the exact file:line that implements it, or `NONE` |
| Status | `ENFORCED` / `PARTIAL` / `DOCUMENTED-ONLY` / `DEAD` / `CONTRADICTED` |
| Evidence | the code path, test, or log line that proves the status |
| Hook-coupled? | yes/no -- does it only work because a hook fires? |
| Post-plugin plan | `keep-as-is` / `port-to-plugin` / `port-to-MCP` / `demote-to-advisory` / `delete` |

Rules for this matrix:
- `ENFORCED` requires a runtime code path **and** evidence it executes. A policy referenced only
  in a prompt template is `DOCUMENTED-ONLY`, not `ENFORCED`.
- `CONTRADICTED` = the policy says X and the code does not-X. Flag every one of these loudly;
  these are the highest-value findings.
- Reconcile the three policy locations (`docs/policies/`, `~/.claude/policies/`, `policies/`).
  State explicitly which one is canonical after this change, and make the other two either
  generated mirrors or deleted. Three divergent copies is not an acceptable end state.

**FR-3: Classify each policy by whether it survives de-hooking.**
Policies whose only enforcement mechanism is a `PreToolUse` block (e.g. tool gating, encoding
validation, path validation) will lose their teeth when hooks are removed. For each, decide and
document one of:
- move the check into the plugin's agent instructions (advisory, model-enforced),
- move it into an MCP tool the agent must call (explicit, still deterministic),
- move it to a git pre-commit hook or CI gate (deterministic, but late),
- accept the loss and delete the policy.

Do not silently drop enforcement. Every demotion must be a recorded decision.

**Acceptance:** matrix committed to `docs/reports/policy-implementation-audit-v2.md`, with a
summary count per status and a ranked list of the top contradictions.

## 5. Workstream B -- Remove Hook-Based Execution

**FR-4: Delete `PreToolUse` and `PostToolUse` hooks entirely.**
Rationale (state this in the ADR): two synchronous Python process spawns per tool call, each with
a 60s timeout, on `matcher: ""`. On a long multi-hundred-tool task this is the dominant latency
and a single-point failure surface -- a hook crash blocks the tool call.

**FR-5: Remove `UserPromptSubmit` orchestration from the hot path.**
`scripts/3-level-flow.py` must no longer run automatically on every prompt. Its capability is not
deleted -- it becomes explicitly invocable (see FR-7).

**FR-6: State the trade-off honestly in an ADR.**
Removing hooks converts the engine from *always-on and involuntary* to *opt-in and explicit*.
That is the user's stated intent, but the consequence -- policies no longer auto-enforce on
sessions where the plugin is not invoked -- must be written down in
`docs/architecture/ADR-006-hook-free-execution.md`, not discovered later.

**FR-7: Replace hooks with explicit entry points.** Minimum set:
- Slash commands for the pipeline phases a user actually wants on demand
  (e.g. plan/decompose, implement, review, document, release).
- MCP tools for anything that must be deterministic rather than model-judged.
- A single command that runs the full Steps 0-8 pipeline for users who want the old behaviour.

**FR-8: Decide the fate of `Stop` and `Notification` hooks explicitly.**
These are cheap and fire once, not per tool call. Recommend keeping `Stop` (session save) and
`Notification` (beep) unless the user says otherwise -- but make it a stated decision, not an
oversight. Confirm with the user before deleting session persistence.

**Constraint:** After this workstream, a session with the plugin installed but never invoked must
behave exactly like stock Claude Code -- zero added latency, zero spawned processes.

## 6. Workstream C -- Master-KG-Driven Agent and Skill Selection

**FR-9: Resolve the library count drift first.**
`master_graph.md` reports 541 agents / 1030 skills; the filesystem has 506 agents / 993 skills.
Determine which is stale, rebuild via `knowledge-graph/_master/build_master.py`, and run
`validate.py` + the invariant checker until clean. Selection built on a stale graph is worthless.
If the drift is a library-repo bug, file it there and pin a known-good graph version meanwhile.

**FR-10: Selection must query the graph, never a hardcoded list.**
Any place in this repo that names an agent or skill as a string literal is a defect to be removed.
Selection input: task description + detected domain + `combined_complexity_score` (1-25 scale --
do not treat as 1-10) + call-graph risk signals. Selection output: a ranked agent set with the
graph edges that justified each pick.

**FR-11: Selection must be explainable.**
For every selected agent, emit: agent name, source domain, matched skills, the KG edge path that
led to it, and a confidence score. A selection with no traceable edge path is a bug.

**FR-12: Handle the no-match and low-confidence cases.**
Define the fallback explicitly (e.g. `general-purpose` / `claude` catch-all) and log it as a
degraded selection rather than pretending it was a match.

**FR-13: Respect the existing model fallback protocol.**
Sonnet rate limit -> retry the same agent with an opus override, preserving the full prompt, and
log the fallback. Opus rate limit -> escalate to the user. This is already a standing rule; the
new selector must not bypass it.

## 7. Workstream D -- Package as a Claude Code Plugin

**FR-14: Produce an installable plugin.**
The engine's capability must be delivered as a Claude Code plugin -- a manifest plus bundled
commands, agents, skills, and MCP server references -- installable in one step, with no manual
`settings.json` surgery by the user.

**Before building:** verify the current plugin manifest schema and directory contract against the
official Claude Code documentation (use the `claude-code-guide` agent). Do not build against a
remembered schema. Confirm at minimum: manifest filename and location, how commands/agents/skills
directories are discovered, how bundled MCP servers are declared, and whether hooks bundled in a
plugin are opt-in per install.

**FR-15: The plugin must be self-contained.**
It must not depend on the user having hand-edited `~/.claude/settings.json`, and must not depend
on absolute Windows paths. Use `path_resolver.py` for all path construction (existing project rule).

**FR-16: Bundle, do not duplicate.**
Agents and skills come from `claude-global-library` by reference or by a generated bundle step --
not by copying 506 agent directories into this repo. Define the sync mechanism and its staleness
check.

**FR-17: Cross-platform correctness.**
Primary target is Windows 11 with PowerShell. UTF-8 encoding, ASCII-only in Python source
(cp1252-safe). No POSIX-only assumptions in the install path.

**FR-18: Uninstall must be clean.**
Removing the plugin leaves no orphaned hooks, no stale MCP registrations, and no leftover
`settings.json` entries.

> **SUPERSEDED 2026-08-01 — this requirement as written is NOT ACHIEVABLE. Original text retained
> above so the intent stays visible; the operative version lives in
> `docs/phase-0-requirements/prd-v2.md`.**
>
> Measured by the FR-14a spike (`docs/phase-1-architecture/plugin_schema_spike.md`, item 4):
> `claude plugin uninstall` empties `enabledPlugins` and `extraKnownMarketplaces` to `{}` but
> **never removes the keys**, and leaves an orphaned plugin cache directory marked `.orphaned_at`
> which **`claude plugin prune` does not clean**. No plugin-side execution point exists to
> intercept this — the residue is created by Claude Code after the plugin is already gone.
>
> The requirement was written against an assumption about uninstall behaviour that turned out to be
> false. It is not a case of the implementation falling short of the bar; the bar was unreachable by
> anyone. Revised disposition:
> - **FR-18** narrowed to PLUGIN-ATTRIBUTABLE residue only — what the plugin creates, the plugin removes.
> - **FR-24** added (new): a documented, user-run cleanup runbook for the residue that FR-18 provably
>   cannot reach.
> This is a narrowing PLUS a named replacement, not a narrowing alone.

## 8. Non-Functional Requirements

- **NFR-1 (latency):** With the plugin installed but not invoked, added per-tool-call overhead
  must be **zero** processes and effectively 0 ms. This is the primary success metric.
- **NFR-2 (long-task safety):** No component may impose a fixed per-call timeout that can abort a
  long-running task. The 60s/120s hook timeouts are exactly the failure mode being removed.
- **NFR-3 (observability):** Losing PostToolUse tracking must not mean losing telemetry. Define
  where session/step/tool metrics come from after de-hooking, or state explicitly that they are
  dropped and why that is acceptable.
- **NFR-4 (no silent regression):** Every capability that exists today via hooks must appear in
  the audit matrix with a decided disposition. "It disappeared" is not a disposition.
- **NFR-5 (testability):** Plugin install, invoke, and uninstall must each be covered by a test.

## 9. Deliverables and Order

Strictly sequential -- each gate must pass before the next starts.

| # | Deliverable | Gate |
|---|-------------|------|
| 1 | `docs/reports/policy-implementation-audit-v2.md` (FR-1..FR-3) | User reviews and approves the matrix before any code is deleted |
| 2 | `docs/architecture/ADR-006-hook-free-execution.md` (FR-6) | Trade-off accepted in writing |
| 3 | KG rebuild + validation clean (FR-9) | `validate.py` and invariants pass; counts reconciled |
| 4 | KG-driven selector with explainable output (FR-10..FR-13) | Selector reproduces sane picks on 10 sample tasks |
| 5 | Plugin skeleton verified against live plugin docs (FR-14) | Installs cleanly on Windows; uninstalls leaving no PLUGIN-ATTRIBUTABLE residue **(gate text corrected 2026-08-01 — "uninstalls cleanly" was unachievable, see the FR-18 supersession note above and FR-24)** |
| 6 | Hook removal + explicit entry points (FR-4..FR-8) | NFR-1 measured and met |
| 7 | Migration guide + CHANGELOG + VERSION bump to 2.0.0 | Docs governance rules satisfied |

**Deliverable 1 is a hard gate.** No hook may be deleted before the audit says what that hook was
actually enforcing.

## 10. Constraints

- Governing rules stay in force: `rules/11` (max 5 root doc files), `rules/12` (docstrings only,
  no inline narration), `rules/44` (SRS lifecycle), `rules/45` (UML lifecycle),
  `rules/46` (architecture docs).
- Git and GitHub operations go through the `git-ops` / `github-api` MCP servers, not raw CLI.
- This is a breaking change: version 2.0.0, with a migration guide for the existing hook setup.

## 11. Open Decisions (confirm with the user before building)

1. **Stop + Notification hooks:** keep or remove? (Recommendation: keep -- they are cheap, fire
   once, and `Stop` carries session persistence.)
2. **Auto-enforcement loss:** accepted? Policies will only apply when the plugin is explicitly
   invoked. Confirm this is the intended trade, since it is the direct consequence of FR-4/FR-5.
3. **Canonical policy location:** which of the three becomes the single source of truth?
4. **Library coupling:** does the plugin bundle a pinned snapshot of the library, or read the live
   workspace checkout?
5. **Distribution:** private plugin marketplace under `techdeveloper-org`, or local install only?

## 12. Acceptance Criteria

- **AC-1:** All 46 policies appear in the audit matrix with an evidenced status and a decided
  post-plugin disposition.
- **AC-2:** `PreToolUse` and `PostToolUse` hooks are gone from `settings.json`; an uninvoked
  session spawns zero engine processes.
- **AC-3:** Every pipeline capability that previously ran via `UserPromptSubmit` is reachable
  through an explicit command or MCP tool.
- **AC-4:** Zero hardcoded agent or skill name literals remain in selection code; every selection
  returns a traceable KG edge path.
- **AC-5:** Master KG counts match the filesystem, and `validate.py` passes.
- **AC-6:** The plugin installs, is invoked, and uninstalls cleanly on Windows 11 / PowerShell,
  each step covered by a test.
- **AC-7:** No long-running task can be aborted by a fixed per-call engine timeout.
